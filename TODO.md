# DoorKing TODO

- [ ] **1. The export ignores credential expiry.** `class-fsbhoa-doorking-export.php` selects credentials by status only, never `expiration_date`. Nothing sets a real DoorKing expiry today (the importer and PIN rotation use 2099-12-31, others are blank), so it does no harm yet. If expiry dates are used later, skip credentials whose `expiration_date` is before today (valid through the expiry date, like the UHPPOTE controllers and the kiosk). An expired credential would only drop out at the next export.
- [ ] **2. The import's menu clicks use screen positions.** `DK_Sync.ahk` opens File → Import → Import Now and Action → Send Data Now by clicking coordinates measured on the office PC. On the workbench PC (2026-10-11) a click missed: the script opened Send Data Now where it wanted the Import dialog, failed with "Import dialog did not appear", and the change was never imported. Use `MenuSelect` with the menu items' names instead, as the stream restart already does for File → Exit (needs the exact wording, e.g. "Import Now" or "Import Now..."; a screenshot of the open menus gives it). The gate rows in Send Data Now (`GateRowsY`) are also screen positions; select them by account name if the list allows it.
- [ ] **3. The import can't tell when the send is finished.** After OK in Send Data Now, RAM shows a status window (`Cancel Session`, `Close`, `Less <<`, a `TBDMyListBox` list with one row per account and its Status, such as "Succeeded"). The rows aren't window text, and `ControlGetItems` can't read the list. With data to send, RAM prepares for over a minute before it connects to the panel (OK at 15:53:32, panel link at 15:54:51, "Download Data" at 15:54:56). The script now waits for `Cancel Session` to be enabled and then greyed out, but it was never seen enabled, so its 30-second fallback closes the window and minimizes RAM mid-send. The send still completes (closing the window doesn't cancel it), but the result window then pops up over a minimized RAM and stays open, and while a RAM dialog is open the stream watch won't restart RAM. Find a dependable end signal: how the buttons and the list behave during a session (Window Spy), reading the list another way (e.g. accessibility), or waiting until the window stops changing. Then log each account's Status and treat anything but "Succeeded" as a failure.
- [ ] **4. The stream watch's RAM restart can fail right after an import.** On 2026-10-12, 5 seconds after an import and send finished (17:06:12), the watch found no RAM connection and began restarting RAM. One second later it failed with "Stream watch ERROR: Target control not found" (`automation_testbed.log`). A test on 2026-10-13 with no import running worked: the stream was back 12 seconds after `vehicle_service` started. The likely cause, not confirmed:
  - RAM reconnects its stream for every job, so right after a send the connection can be closed for a moment, and the watch restarted RAM while RAM was reconnecting by itself. Fix: don't restart RAM until the stream has been missing for two checks in a row, or for some time after an import ends (for example 60 seconds).
  - `RestartRam()` waits for any RAM dialog (`ahk_class #32770`) after File → Exit, and probably caught the send-result window (item 3) instead of the backup question. That window has `Cancel Session` and `Close` but no `Cancel`, so `ControlClick("Cancel", dlg)` threw before the script's own "RAM asked something else" error. Fix: before File → Exit, close any open RAM dialog or skip the restart, and click Cancel only through `FindButton()`, logging the dialog's title and text when it isn't found.
